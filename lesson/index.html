Teleoperate a Humanoid's Upper Body with VR Controllers

The ik-teleop lesson · from an empty folder to "I move my hand, the robot follows" · written for students with no robotics background · MuJoCo + differential inverse kinematics + WebXR

This course walks you through building a VR teleoperation system that actually works: put on a PICO headset, squeeze the grip button on the controller, and the humanoid robot's hands — in simulation, and later on the real machine — precisely mirror your hand motion. More importantly, by the end you can explain why every line of code is the way it is.

The design philosophy is one sentence: the yellow cubes (mocap targets) are the only interface. The three input sources are just different ways of writing poses into the cubes; the IK only ever looks at the cubes, never at the sources; the sim viewer and the real robot both just consume the joint angles the IK produces. Every stage can be swapped and tested on its own.

§2 Meet MuJoCo and the robot model

2.1 Where robots come from: URDF, MJCF, and our choice

A robot's "body file" (link sizes, joint axes, limits, display meshes) is usually a URDF (the ROS-world standard) or an MJCF (MuJoCo's own XML). MuJoCo can load URDF directly, but URDF has no concept of actuators, keyframes, or sites, so the community maintains mujoco_menagerie — a zoo of curated, high-quality MJCF models.

The real target of this project is Fauna Robotics' humanoid Sprout (6-DoF arms + 1-DoF grippers; systems paper arXiv:2601.18963). Its URDF/MJCF ships only inside the login-gated Fauna SDK — there is no public download. So the course uses the Unitree G1 from the menagerie (BSD-3 license, 7-DoF arms) as a stand-in with the same dual-arm humanoid topology. Swapping in Sprout later means adding one RobotSpec in src/teleop/robot.py (see 2.4) — nothing else changes.

2.2 Downloading the model: src/teleop/tools/setup_assets.py

38 MB of mesh files don't belong in git, so uv run setup-assets downloads them. It uses git's sparse checkout to fetch only the unitree_g1/ folder, not the whole zoo:

git clone --depth 1 --filter=blob:none --sparse https://github.com/google-deepmind/mujoco_menagerie.git
git sparse-checkout set unitree_g1      # just this one robot

Then it copies our scene file assets/scene_teleop.xml next to g1.xml. Why must it sit there? A classic MuJoCo trap:

Pitfall! Relative asset paths in MJCF (g1.xml says meshdir="assets") resolve against the directory of the main XML file, not the file that was included. Put the scene one directory up and <include file="unitree_g1/g1.xml"/> fails with exactly: Error opening file 'assets/mujoco_menagerie/unitree_g1/pelvis.STL'. We reproduced this. Hence: the scene must live beside g1.xml, and setup-assets copies it there for you.

2.3 The scene file: assets/scene_teleop.xml

Scene = robot + floor + light + two mocap target cubes (the protagonists of §4):

<mujoco model="g1_teleop">
  <include file="g1.xml"/>                 <!-- the whole robot, one line -->
  <worldbody>
    <light pos="0 0 3.5" dir="0 0 -1" directional="true"/>
    <geom name="floor" type="plane" size="0 0 0.05" material="teleop_floor"/>

    <!-- Left-hand target (red). mocap="true": no joints, no physics;
         its pose is whatever you write into it. -->
    <body name="left_target" mocap="true" pos="0.25 0.25 0.9">
      <geom type="box" size="0.035 0.035 0.035" contype="0" conaffinity="0"
            rgba="0.90 0.25 0.20 0.45"/>
      <geom type="box" size="0.045 0.009 0.009" pos="0.055 0 0" .../>  <!-- orientation "nose" -->
    </body>
    <!-- right_target (green) is identical -->
  </worldbody>
</mujoco>

contype="0" conaffinity="0" removes the cubes from all collision — they are a visualization of intent, not physical objects. The little bar sticking out along +x lets you see the target's orientation.

2.4 Loading and indexing: src/teleop/robot.py

MuJoCo's world is two objects: MjModel (immutable: structure, limits, meshes) and MjData (changes every frame: joint angles qpos, world poses of every body). robot.py does three things: load, resolve names into numeric indices, and own the target read/write.

Every robot-specific string is gathered into one RobotSpec — this is the entire secret of "swap robots by editing one place":

G1 = RobotSpec(
    name="g1",
    scene_file="unitree_g1/scene_teleop.xml",
    home_keyframe="stand",                      # ships inside g1.xml
    arms=(
        ArmSpec(
            name="left",
            joint_names=("left_shoulder_pitch_joint", "left_shoulder_roll_joint",
                         "left_shoulder_yaw_joint", "left_elbow_joint",
                         "left_wrist_roll_joint", "left_wrist_pitch_joint",
                         "left_wrist_yaw_joint"),   # shoulder → wrist, 7 joints
            ee_body="left_wrist_yaw_link",          # the body the hand is welded to
            ee_offset=(0.08, 0.0, 0.0),             # palm = wrist origin + 8 cm (menagerie convention)
            mocap_body="left_target",
        ),
        # right is symmetric ...
    ),
)
Pitfall! A joint has TWO index spaces. The G1 has nq=36 (length of qpos) but nv=35 (velocity/jacobian space). Why the difference? The floating base takes 7 numbers in qpos (3 position + 4 quaternion) but only 6 in velocity space (3 linear + 3 angular). So robot.py stores both qpos_ids (for reading/writing joint angles) and dof_ids (for slicing jacobian columns) per arm: 
qpos_ids = np.array([self.model.jnt_qposadr[j] for j in joint_ids])
dof_ids  = np.array([self.model.jnt_dofadr[j]  for j in joint_ids])
Mixing them up is the classic off-by-one bug in MuJoCo code.
Try it uv run setup-assets prints nq/nv and both palm positions when it finishes. Then print all 30 joint names and find the 14 that belong to the arms: uv run python -c "import mujoco; m = mujoco.MjModel.from_xml_path('assets/unitree_g1/g1.xml'); print([m.joint(i).name for i in range(m.njnt)])"

§3 Quaternions and forward kinematics: where is the hand now?

3.1 Quaternions — the only four facts you need: src/teleop/quat.py

Orientation is represented by a unit quaternion — four numbers, no gimbal lock. The whole repo relies on exactly four facts:

  1. The component order is wxyz (w first) — MuJoCo's convention. WebXR and SciPy both use xyzw (w last)! §8 converts exactly once, at the boundary.
  2. Composition of two rotations is quaternion multiplication: quat.mul(q1, q2) ≈ apply q2 first, then q1 (like the matrix product R1·R2).
  3. The inverse of a unit quaternion is its conjugate: quat.conj(q), so mul(q, conj(q)) = identity.
  4. An orientation error can be compressed into one 3-vector (axis × angle):
def error_world(q_target, q_current):
    """Rotation vector (world frame, axis*angle, radians) taking q_current onto q_target.

    Math: the world-frame error rotation is q_err = q_target ⊗ q_current⁻¹
    (apply q_err *after* the current rotation and you land exactly on the
    target); mju_quat2Vel is its log map (quaternion → rotation vector).
    """
    q_err = mul(q_target, conj(q_current))
    out = np.empty(3)
    mujoco.mju_quat2Vel(out, q_err, 1.0)
    return out

That 3-vector is the "orientation error" input of §5's IK: spin at this angular velocity for one second and the orientation lands on target. All the arithmetic is delegated to MuJoCo's battle-tested mju_* C functions; we only wrap them so the rest of the code reads like plain math.

3.2 Forward kinematics: robot.ee_pose()

Forward kinematics (FK): given joint angles, where is the hand? MuJoCo's mj_forward(model, data) computes the world pose of every body in one call. Our "palm pose" = the wrist body's pose, offset 8 cm along its own x-axis to the palm center:

def ee_pose(self, arm):
    body = self.data.body(arm.ee_body_id)
    rotation = body.xmat.reshape(3, 3)          # wrist's world rotation matrix
    return Pose(body.xpos + rotation @ arm.ee_offset,  # origin + offset
                body.xquat.copy())                     # orientation = wrist's

Inverse kinematics is the other direction: given "where the hand should be", find the joint angles. FK has a unique answer computed in one line; IK generally has no closed-form answer — that's the central problem of this course, and it's §5.

§4 Targets = mocap cubes (and a mouse mode for free)

The red and green cubes from §2 are mocap bodies: no joints, no gravity, no collisions; their pose equals whatever you write into data.mocap_pos / data.mocap_quat. We decree: "where the hands should be" exists only inside these two cubes.

# The complete target read/write in robot.py (really, this is all of it):
def target_pose(self, arm):              # read: the IK asks "where to?" every frame
    return Pose(self.data.mocap_pos[arm.mocap_id].copy(),
                self.data.mocap_quat[arm.mocap_id].copy())

def set_target(self, arm, pose):         # write: a source says "go here" every frame
    self.data.mocap_pos[arm.mocap_id] = pose.pos
    self.data.mocap_quat[arm.mocap_id] = pose.quat

On reset() the cubes are parked exactly on the palms (target = current state, error = zero), so every mode starts with the robot perfectly still — nothing ever jumps is a principle that runs through the entire project.

Mouse mode: the best code is no code

MuJoCo's interactive viewer natively supports dragging mocap bodies: select one, and every viewer.sync() writes your drag straight into data.mocap_pos/quat. (We checked the MuJoCo 4.0.1 C++ source, simulate.cc: in passive mode, sync applies mjv_applyPerturbPose, which writes only to mocap bodies.) So the "mouse mode" implementation is — nothing at all:

# src/teleop/sources/__init__.py
class MouseSource(TargetSource):
    """The "do nothing" source, and that's the point: the viewer drags the
    cubes for us, and the IK only ever looks at the cubes."""
Try it uv run test-in-sim --source mouse, then: double-click the red cube to select it → Ctrl+right-drag to translate (add Shift for the horizontal plane), Ctrl+left-drag to rotate. The arm chases it in real time. Congratulations — you are already "teleoperating"; the input device just happens to be a mouse.

§5 Differential inverse kinematics: the heart of the project (src/teleop/ik.py)

IK answers: "the hand is here, the target is there — how should each joint turn?" We never solve for a final configuration. Instead, 60 times a second, we answer a much smaller question:

Idea Find a joint velocity dq that nudges the hand toward the target; take one small step; look again; repeat. Target moving? Doesn't matter — we re-aim every frame, so tracking a moving VR controller comes for free. This is differential IK, and it is the industry-standard approach for VR teleoperation.

5.1 Error → desired velocity (twist)

twist = np.empty(6)
twist[:3] = settings.pos_gain * (target.pos - current.pos)   # position error × gain
twist[3:] = settings.rot_gain * quat.error_world(target.quat, current.quat)

Gains have units of 1/second: "close this fraction of the error per second". pos_gain=12 means the hand rushes at 12 × error — the smaller the error, the gentler the motion. Smoothing is built in.

5.2 The jacobian: the bridge between joint and hand velocity

The jacobian J answers "if each joint turned at 1 rad/s, how would the hand move?": hand 6-D velocity = J · joint velocities. MuJoCo hands it to us:

jacp = np.zeros((3, model.nv)); jacr = np.zeros((3, model.nv))
mujoco.mj_jac(model, data, jacp, jacr, current.pos, arm.ee_body_id)  # taken at the palm point
jac = np.vstack([jacp, jacr])[:, arm.dof_ids]   # keep this arm's 7 columns → 6×7

Note the column slice uses dof_ids (the §2 pitfall): jacobians live in nv space.

5.3 Damped least squares (DLS): inverting without drama

We want J·dq = twist. J isn't square (6×7), and naive "division" explodes near a singularity (e.g. a fully stretched arm): some directions of hand motion become impossible, and forcing them demands infinite joint speed. The fix is a little damping λ in the inversion:

# dq = Jᵀ (J Jᵀ + λ² I)⁻¹ · twist      — textbook name: damped least squares
jjt = jac @ jac.T
jjt[np.diag_indices_from(jjt)] += settings.damping ** 2
dq = jac.T @ np.linalg.solve(jjt, twist)

Intuition for λ: accuracy traded for stability. λ=0 is the exact least-squares solution (dangerous); large λ is sluggish everywhere. We use 0.05.

5.4 The nullspace: where the spare freedom goes

Seven joints chasing a 6-D pose leaves one degree of freedom spare: the elbow can swing without the hand feeling it. Left unmanaged, the elbow slowly drifts somewhere awkward. We spend the spare freedom on "gently pull toward a comfortable home posture" — but it must be projected into the nullspace (the directions where J·dq = 0), guaranteed invisible to the hand:

dq_posture = settings.posture_gain * (arm.q_home - data.qpos[arm.qpos_ids])
dq += dq_posture - np.linalg.pinv(jac) @ (jac @ dq_posture)   # (I − J⁺J)·dq_posture
Pitfall! (measured war story #1) The projection must use the exact pseudo-inverse np.linalg.pinv(jac). Our first version lazily reused the damped inverse from 5.3 — the posture term "leaked" into task space and fought the tracking, so the hand stopped 11 mm short of the target, forever (measured). With the exact projector: 0.00 mm. To reproduce: change that line back to jac.T @ np.linalg.solve(jjt, jac @ dq_posture) and watch uv run pytest tests/test_ik.py -k reaches fail.
Pitfall! (measured war story #2) In the G1's stand keyframe the arms hang nearly straight down — a pose that is close to singular (smallest singular value 0.011; damping squashes velocity in that direction to ~5%). Worse, keeping the "hanging-arm palm orientation" while lifting the hand to chest height jams the wrist_pitch joint into its +1.61 rad limit: orientation error stuck at 38°, dragging position off by 40 mm too. That is why §7's trajectory first lifts the hands and pitches the palms forward before drawing the 8: designing good targets matters as much as a good solver.

5.5 Finishing touches: speed cap, limits, integration

peak = float(np.max(np.abs(dq)))
if peak > settings.max_joint_vel:          # uniform scale-down (keeps the hand's direction)
    dq *= settings.max_joint_vel / peak
...
q = robot.data.qpos[arm.qpos_ids] + dq * dt            # integrate one small step
robot.data.qpos[arm.qpos_ids] = np.clip(q, arm.joint_min, arm.joint_max)

The speed cap protects real motors (§9 reuses it directly); limits are hard-clipped with np.clip. The two arms share no joints, so each solves its own little 6×7 problem — simpler code, simpler mental model.

Try it ① Set IKSettings.damping to 0.5 and run uv run test-in-sim — feel the sluggishness everywhere. Then 0.001, and drag the mouse target far out of reach — watch the jitter. ② Set posture_gain to 0 and draw figure-8s for a while — watch the elbow wander. ③ uv run pytest tests/test_ik.py -v: five convergence tests are this chapter's "proof".

§6 The simulation main loop: test-in-sim (src/teleop/run_sim.py)

Everything is in place; the main loop has exactly 4 lines of real work, 60 times per second:

targets = source.get_targets(t)   # 1. ask the source: where should the hands go? (None = no opinion)
if targets is not None:
    robot.set_targets(targets)    # 2. write into the mocap cubes
errors = ik.step(robot, dt)       # 3. each arm takes one small step toward its cube
viewer.sync()                     # 4. draw (and apply your mouse drags to the mocap cubes)
Important We never call mj_step (physics integration)! This is pure kinematics — a puppet show: the IK writes joint angles directly and mj_forward merely converts them into world poses. Benefits: the robot can never fall over, there are no motor gains to tune, and the first run never ends in frustration. Want real physics? Exercise 5 in §10 shows how to switch to position actuators + mj_step.

The rest of the file is periphery: argparse picks the source (--source trajectory|mouse|pico), a 60 Hz pacing loop (sleep off whatever time is left after the work), a tracking-error printout every 2 seconds, and the --headless mode — run N seconds without a window and exit non-zero if the final error exceeds 30 mm. That mode is the end-to-end smoke test for CI/servers, and your fastest alarm when you break the IK.

Try it uv run test-in-sim --headless --duration 15: watch the error fall from tens of millimeters during the lift to 5–14 mm while drawing the 8. Then deliberately set pos_gain to 1 and watch it FAIL.

§7 The first target source: a scripted figure-8 (src/teleop/sources/trajectory.py)

The source interface is small enough to read in one glance (src/teleop/sources/__init__.py):

class TargetSource:
    def start(self): ...                       # once, before the loop (e.g. start a server)
    def get_targets(self, t) -> TargetFrame | None: ...   # every frame: new targets, or nothing to say
    def stop(self): ...                        # once, after the loop

The trajectory source has two phases, both starting smoothly from wherever the hands are (that no-jumps principle again):

  1. Lift-in (first 3 s): smoothstep (3x²−2x³, zero velocity at both ends) carries both hands from the hanging pose to a spot in front of the chest, LIFT_OFFSET=(0.22, 0, 0.18), while pitching the palms forward about the world y-axis by LIFT_PITCH=−0.6 rad — the antidote to §5's war story #2. The number was found by a measured sweep: 0.0 jams the wrist limit (38° residual); −0.6 tracks with 0.0° orientation error.
  2. The figure-8: a lemniscate in the y–z plane, right hand mirrored:
u  = 2π · (t − ramp_time) / period
Δy = A · sin(u)                 # A = 0.12 m
Δz = A/2 · sin(2u)              # double frequency → the "∞" shape
left  = rest + lift + (0, +Δy, Δz)
right = rest + lift + (0, −Δy, Δz)        # mirrored, like tai chi
Try it Set amplitude=0.2 and rerun — do the edges of the bigger 8 hit the workspace boundary? (Watch when the printed error grows.) Halve period: speed doubles, and lag = speed ÷ pos_gain. Predict the number, then measure it.

§8 VR: WebXR, coordinate frames, and the clutch

Time to replace the fake input with real controllers. The design choice: WebXR — a web page opened in the Pico's built-in browser reads controller poses and streams them to the PC over a WebSocket. Zero install on the headset (you open one URL), and the PC side adds a single websockets dependency. Unitree's official G1 teleoperation uses this same pattern. (The research-grade alternative — PICO's XRoboToolkit, ~90 Hz native streaming + body tracking — requires building a Unity APK and adb-sideloading it onto every headset: too much setup for a classroom. See §10.)

8.1 The headset page: src/teleop/sources/webxr/index.html

One HTML file is the whole thing (no framework, no build step). The core is ~30 lines:

const session  = await navigator.xr.requestSession("immersive-vr",
                       { requiredFeatures: ["local-floor"] });  // origin on the floor beneath you
const refSpace = await session.requestReferenceSpace("local-floor");

session.requestAnimationFrame(function onFrame(time, frame) {
  session.requestAnimationFrame(onFrame);               // ~72 Hz
  for (const input of session.inputSources) {           // both controllers
    const pose = frame.getPose(input.gripSpace, refSpace);  // may be null — guard it!
    const p = pose.transform.position;      // meters; x right, y up, z backward
    const q = pose.transform.orientation;   // quaternion, xyzw order (!)
    const buttons = input.gamepad.buttons;  // xr-standard: [0]=trigger [1]=grip
    ...pack into JSON...
  }
  ws.send(JSON.stringify({ t, left, right }));          // stream to the PC
});

The page does three more considerate things: it checks isSessionSupported before offering the button; it attaches a WebGL baseLayer and clears the view to a color — the world turns green while you squeeze the grip, a visceral "the robot is following me" signal; and the WebSocket auto-reconnects.

Pitfall! WebXR exists only in a HTTPS (secure) context, and requestSession must be triggered by a user click. There's no real certificate on a LAN, so we use a self-signed certificate: the browser warns once; tap "Advanced → Proceed". The page and the WebSocket share one port, so accepting the warning once unblocks both (the wss certificate exception rides along with the same origin). For wired debugging there's a zero-certificate trick: adb reverse tcp:8443 tcp:8443, then open http://localhost:8443 on the headset — localhost counts as a secure context.

8.2 Coordinate frames: two worlds shake hands (src/teleop/mapping.py)

WebXR: x right, y up, −z forward. MuJoCo: x forward, y left, z up. Standing behind the robot, facing the same way it faces, "push the controller forward" must become "robot +x":

XR_TO_MJ_MAT = [[ 0, 0, -1],      # x_mj = -z_xr   (forward)
                [-1, 0,  0],      # y_mj = -x_xr   (left)
                [ 0, 1,  0]]      # z_mj = +y_xr   (up)
# Positions: multiply by the matrix. Orientations: conjugate by the same
# rotation, R_mj = R_fix · R_xr · R_fixᵀ
# (the same physical rotation, re-expressed in the robot's axes).

The quaternion order flip (xyzw→wxyz) happens once, where pico.py ingests each message; after that the whole repo is wxyz. tests/test_mapping.py pins the directions with known rotations ("a turn about XR's y-axis must become a turn about MJ's z-axis").

8.3 The clutch: the most important interaction design in VR teleop

Absolute mapping would require calibrating "where is the headset relative to the robot?" — nobody wants to do that in a classroom. Relative mapping with a clutch sidesteps it entirely: controller deltas apply to the target only while you hold the grip button; release and the target freezes; reposition your arm comfortably and squeeze again — the target never jumps. Exactly like lifting a mouse to re-center it on the pad.

class Clutch:                           # mapping.py, one per hand
    def update(self, grip_held, controller):
        if not grip_held: release → remember the target, drop snapshots; return frozen target
        if just gripped:  snapshot controller₀ and target₀
        # while held, every frame:
        target.pos  = target₀.pos + scale · (controller.pos − controller₀.pos)
        target.quat = (controller.quat ⊗ controller₀.quat⁻¹) ⊗ target₀.quat
        #              └── world-frame rotation since the grab ──┘

scale is the ergonomics knob: 0.5 = you move 10 cm, the robot moves 5 cm (precision work); 2.0 = big workspace. The --scale CLI flag feeds straight into this (pico source only).

8.4 The PC-side server: src/teleop/sources/pico.py

One port does two jobs: a plain HTTPS GET returns the page above, and /ws upgrades to a WebSocket (the websockets library's process_request hook). The server runs an asyncio loop in a background thread; when the 60 Hz main loop comes asking, it reads only the latest message (an old pose is worthless, hence no queue):

def get_targets(self, t):
    with self._lock:
        snap = self._latest
    if snap is None or time.monotonic() - snap.received_at > STALE_AFTER:
        ... disengage both clutches ...
        return None            # watchdog: data stream died → targets freeze, robot holds
    # per hand: XR→MJ conversion → feed the clutch → new target
    return TargetFrame(left=..., right=...)

On first run it generates a self-signed certificate into .certs/ with cryptography (SAN includes your LAN IP) and prints the URL the headset should open.

Try it Put the PC and the Pico on the same Wi-Fi, run uv run test-in-sim --source pico, and follow the three printed steps. No headset handy? Run uv run pytest tests/test_pico_bridge.py -v and read how a "fake headset" walks the entire WSS pipeline (it proves: pushing 10 cm forward in XR = robot +x 10 cm; release freezes; a dead stream freezes).

§9 Connecting a real robot: test-in-real and safety (src/teleop/run_real.py)

Here's the trick: "real mode" still runs MuJoCo. The simulated robot becomes the kinematic brain — sources move the cubes and the IK chases them exactly as before — and each tick (50 Hz) adds one line: read the simulated arm joint angles and send them to the real robot's position controller.

targets = source.get_targets(t)
if targets is not None:          # None ⇒ watchdog/deadman: hold position
    brain.set_targets(targets)
ik.step(brain, dt)               # sim joints chase the targets (limits + speed cap)
real.send_joint_targets(brain.joint_targets())   # ...and the real robot copies the sim

Safety is layered. Learn the order (AGENTS.md forbids removing any layer):

LayerMechanismWhere
1 Deadmantargets move only while the grip is heldthe clutch (§8.3)
2 WatchdogVR stream silent 0.5 s → targets freezepico.py get_targets
3 Motion limitshard joint-limit clip + per-joint speed capik.py (§5.5)
4 On-robot checksthe hardware driver must re-verify limits itselfreal_robot.py contract

The hardware interface: src/teleop/real_robot.py

All of hardware is compressed into three methods, addressed by MuJoCo joint name:

class RealRobot:
    def connect(self): ...                         # connect; enter compliant/low-gain mode
    def send_joint_targets(self, targets: dict[str, float]): ...  # joint angles [rad] at 50 Hz
    def disconnect(self): ...                      # stop motion; must be safe to call twice

The default implementation, DryRunRobot, prints instead of moving, so uv run test-in-real is always safe to run. FaunaRobot is the slot reserved for the real Sprout: its methods raise NotImplementedError, and a JOINT_TO_MOTOR table waits for you to fill in with the Fauna SDK (Sprout: 6-DoF per arm, 1-DoF grippers; model + SDK behind the login at docs.faunarobotics.com). Mapping the G1's 7-joint arms onto Sprout's 6-joint arms is just another RobotSpec in robot.py — the IK, the sources, and the main loops don't change by a single line.

Try it ① Rehearse the whole real-robot pipeline without a headset: uv run test-in-real --source trajectory --duration 5 — watch the 50 Hz joint command stream print. ② With the headset: uv run test-in-real (defaults: pico source + dry-run robot). ③ Thought experiment: why does the watchdog freeze the targets rather than emergency-stopping the motors? (Hint: what does an arm do when it suddenly loses power?)

§10 Exercises and further reading

Exercises (easy → hard)

  1. Change the trajectory: turn the figure-8 into a circle, then into your initials. You may only touch src/teleop/sources/trajectory.py.
  2. Reproduce both pitfalls: follow the two "Pitfall!" boxes in §5 and reproduce each once, with an error-curve screenshot. You only truly understand a fix once you can resurrect the bug.
  3. Trigger → gripper: the WebXR messages already carry trigger (0–1). Wire it to a printout/visualization (g1.xml has no fingers; on the real robot this becomes Sprout's gripper opening).
  4. Let the waist join in: add the G1's waist joints to the IK's degrees of freedom. (Hint: the arms would then share columns — which assumption of "each arm solves independently" breaks, and what would you do about it?)
  5. Real physics: g1.xml ships position actuators (kp=500). Change run_sim to data.ctrl[...] = IK's qpos + mj_step, and compare with puppet mode: does it oscillate? Can it fall? Why?
  6. The research-grade pipeline: replace the WebXR source with PICO's XRoboToolkit (PC service + Unity client + pip install xrobotoolkit-sdk) — one new TargetSource is all it takes; that's what the interface is for.
  7. Drive the real robot: once you have Fauna SDK access, implement FaunaRobot's three methods and a Sprout RobotSpec. Unloaded first, low gains, hand on the e-stop.
