Teleoperate a Humanoid's Upper Body with VR Controllers

The ik-teleop lesson · from an empty folder to "I move my hand, the robot follows" · written for students with no robotics background · MuJoCo + differential inverse kinematics + WebXR

This course walks you through building a VR teleoperation system that actually works: put on a PICO headset, squeeze the grip button on the controller, and the Booster K1 humanoid's hands — in simulation, and later on the real machine — mirror your hand motion. More importantly, by the end you can explain why every line of code is the way it is. And because every robot-specific fact lives in one spec object, the system supports a second robot, the taller Booster T1, as a payoff you get almost for free (§2.5): every command in this lesson accepts --robot-spec t1.

The design philosophy is one sentence: the yellow cubes (mocap targets) are the only interface. The three input sources are just different ways of writing poses into the cubes; the IK only ever looks at the cubes, never at the sources; the sim viewer and the real robot both just consume the joint angles the IK produces. Every stage can be swapped and tested on its own.

§2 Meet MuJoCo and the robot model

2.1 Where robots come from: URDF, MJCF, and our choice

A robot's "body file" (link sizes, joint axes, limits, display meshes) is usually a URDF (the ROS-world standard) or an MJCF (MuJoCo's own XML). Booster Robotics publishes both for its whole robot family in one official asset repository, booster_assets (BSD-3-Clause) — so the simulation drives the same robot you deploy on, no stand-in needed. We build the course around the K1 and add its bigger sibling, the T1, in §2.5.

We use the MJCF, K1_22dof.xml, and it's worth knowing why: MuJoCo can load the shipped URDF directly, but the URDF import silently drops the floating base joint (the robot gets welded to the world) and carries no actuators or keyframes — MJCF is simply the more complete description for MuJoCo work. The K1 in numbers: 0.95 m, ~19.7 kg, 22 actuated joints = 2 head + 4 per arm + 6 per leg; no waist, no wrists, no hands. Hold onto that "4 per arm" — it reshapes the IK in §5.

2.2 Downloading the models: src/teleop/tools/setup_assets.py

~20 MB of mesh files per robot don't belong in git, so uv run setup-assets downloads them (all robots by default; --robot k1 or --robot t1 for just one). It uses git's sparse checkout to fetch only the folders we need, not Booster's other robots or motion data:

git clone --depth 1 --filter=blob:none --sparse https://github.com/BoosterRobotics/booster_assets.git
git sparse-checkout set robots/K1 robots/T1   # just our robots (~20 MB each)

Which folders those are is not written in this tool — it reads them from the RobotSpec objects of 2.4 (vendor_dir, model_file), so teaching it about a new robot means touching robot.py only. Then it copies each robot's scene file (assets/scene_teleop_k1.xml, assets/scene_teleop_t1.xml) next to the vendor XML it includes. Why must it sit there? A classic MuJoCo trap:

Pitfall! Relative asset paths in MJCF (K1_22dof.xml says meshdir="meshes/") resolve against the directory of the main XML file — the one you pass to MjModel.from_xml_path — not the file that was included. Include the robot from any other directory and every mesh path breaks. Hence: the scene must live beside K1_22dof.xml, and setup-assets copies it there for you. (Try it: copy the scene one directory up and load it — mesh after mesh fails to resolve.)

2.3 The scene file: assets/scene_teleop_k1.xml

Scene = robot + two mocap target cubes (the protagonists of §4). Unusually, Booster's K1_22dof.xml already ships a complete mini-scene of its own — a ground plane, a skybox, two lights — so our wrapper adds only what teleop needs:

<mujoco model="k1_teleop">
  <include file="K1_22dof.xml"/>           <!-- the whole robot (+ its own floor/lights) -->
  <worldbody>
    <!-- Left-hand target (red). mocap="true": no joints, no physics;
         its pose is whatever you write into it. -->
    <body name="left_target" mocap="true" pos="0.2 0.2 0.6">
      <geom type="box" size="0.03 0.03 0.03" contype="0" conaffinity="0"
            rgba="0.90 0.25 0.20 0.5"/>
    </body>
    <!-- right_target (green) is identical -->
  </worldbody>
</mujoco>

contype="0" conaffinity="0" removes the cubes from all collision — they are a visualization of intent, not physical objects. The cubes are deliberately plain: the K1 tracks hand position only (§5), so a target orientation marker would just mislead.

2.4 Loading and indexing: src/teleop/robot.py

MuJoCo's world is two objects: MjModel (immutable: structure, limits, meshes) and MjData (changes every frame: joint angles qpos, world poses of every body). robot.py does three things: load, resolve names into numeric indices, and own the target read/write.

Every robot-specific string is gathered into one RobotSpec — this is the entire secret of "swap robots by editing one place" (§2.5 cashes it in):

K1 = RobotSpec(
    name="k1",
    scene_file="booster_k1/scene_teleop.xml",   # our scene, after setup-assets installs it
    scene_template="scene_teleop_k1.xml",       # ...and its source in assets/
    vendor_dir="robots/K1",                     # where it lives in booster_assets (§2.2)
    model_file="K1_22dof.xml",                  # the vendor MJCF the scene includes
    base_joint="world_joint",
    home_base_height=0.552,     # trunk height that puts the feet on the floor (measured)
    home_joint_angles=(         # the model ships NO keyframe — we author home here
        ("aaleft_shoulder_pitch_joint", -0.25),
        ("left_shoulder_roll_joint", -1.40),
        ("left_elbow_yaw_joint", -0.60),
        # ... right side mirrors with opposite signs
    ),
    track_orientation=False,    # 4-DoF arms: position-only tracking (§5)
    arms=(
        ArmSpec(
            name="left",
            joint_names=("aaleft_shoulder_pitch_joint",  # vendor name, 'aa' and all
                         "left_shoulder_roll_joint",
                         "left_elbow_pitch_joint",       # forearm pronation
                         "left_elbow_yaw_joint"),        # the actual elbow bend
            ee_body="left_elbow_yaw_link",   # last arm body (forearm + hand cap)
            ee_offset=(0.0, 0.18, 0.0),      # palm center: the forearm runs along +y
            mocap_body="left_target",
        ),
        # right is mirrored (ee_offset y = -0.18, elbow bend sign flipped) ...
    ),
)
Pitfall! (names) Two naming lessons hide in that spec. First: several K1 names carry a vendor aa prefix (aaleft_shoulder_pitch_joint, aahead_yaw_joint) — copy vendor names verbatim, oddities included; "fixing" them breaks every lookup. Second: names can lie about function. We measured it: on the K1, elbow_pitch spins the forearm about its own axis (pronation — the hand point doesn't move at all), while elbow_yaw is the actual elbow bend. Trust measurements, not names.
No keyframe? Many vendor models ship a named home pose (a <keyframe>); the K1 doesn't, and its qpos=0 is a flying T-pose — arms straight out, feet 0.45 m above the floor. So Robot.reset() builds home by hand: drop the base to 0.552 m (feet exactly on the floor — measured), then apply the authored arm angles. Not every robot file is "batteries included".
Pitfall! (indices) A joint has TWO index spaces. The K1 has nq=29 (length of qpos) but nv=28 (velocity/jacobian space). Why the difference? The floating base takes 7 numbers in qpos (3 position + 4 quaternion) but only 6 in velocity space (3 linear + 3 angular). So robot.py stores both qpos_ids (for reading/writing joint angles) and dof_ids (for slicing jacobian columns) per arm: 
qpos_ids = np.array([self.model.jnt_qposadr[j] for j in joint_ids])
dof_ids  = np.array([self.model.jnt_dofadr[j]  for j in joint_ids])
Mixing them up is the classic off-by-one bug in MuJoCo code.
Try it uv run setup-assets prints nq/nv and both palm positions when it finishes. Then print all 23 joint names (1 free + 22 hinges) and find the 8 that belong to the arms: uv run python -c "import mujoco; m = mujoco.MjModel.from_xml_path('assets/booster_k1/K1_22dof.xml'); print([m.joint(i).name for i in range(m.njnt)])"

2.5 The payoff: a second robot, the Booster T1

Everything robot-specific sits in one spec — so let's prove it. The Booster T1 is the K1's bigger sibling: 1.2 m, 23 joints — the K1's layout plus one waist yaw joint (which our teleop leaves alone, like the head and legs). Its arms are again 4-DoF with no wrists, so everything §5 says about the DoF budget carries over unchanged. Supporting it took exactly three things, and zero changes to the IK, the sources, or the main loops:

  1. One RobotSpec (T1 in robot.py) with freshly measured numbers: feet-on-floor trunk height 0.687 m (vs the K1's 0.552), palm center 0.216 m along the forearm (vs 0.18), and the same relaxed home pose — the sign conventions transfer verbatim.
  2. One scene file, assets/scene_teleop_t1.xml: identical to the K1 scene except it includes T1_23dof.xml and raises the camera framing for the taller robot.
  3. One joint→motor table in the real driver (§9) — eight entries.

Measuring the spec is a half-hour of the same probing you did in the "Try it" above, and it re-confirmed both §2.4 naming pitfalls in new ways. The aa prefixes moved: the K1 writes aaleft_shoulder_pitch_joint, the T1 writes plain left_shoulder_pitch_joint — but keeps aahead_yaw_joint. (Copy vendor names verbatim; never assume two robots from the same vendor spell alike.) And the elbow lie is hereditary: on the T1 too, elbow_pitch is pure forearm pronation — rotate it by a full radian and the palm point moves 0.0 mm (measured) — while elbow_yaw is the real bend. The T1 model also ships no keyframe, so its home pose is authored in the spec, exactly like the K1's.

Try it uv run test-in-sim --robot-spec t1 — the taller robot draws the same figure-8 (tracking error settles at 5–10 mm, same as the K1; the headless smoke test passes for both). Every entry point takes the flag: test-in-sim, test-in-real, render-videos; setup-assets calls it --robot and also accepts all. A third robot would follow the same recipe — spec, scene, driver table.

§3 Quaternions and forward kinematics: where is the hand now?

3.1 Quaternions — the only four facts you need: src/teleop/quat.py

Orientation is represented by a unit quaternion — four numbers, no gimbal lock. The whole repo relies on exactly four facts:

  1. The component order is wxyz (w first) — MuJoCo's convention. WebXR and SciPy both use xyzw (w last)! §8 converts exactly once, at the boundary.
  2. Composition of two rotations is quaternion multiplication: quat.mul(q1, q2) ≈ apply q2 first, then q1 (like the matrix product R1·R2).
  3. The inverse of a unit quaternion is its conjugate: quat.conj(q), so mul(q, conj(q)) = identity.
  4. An orientation error can be compressed into one 3-vector (axis × angle):
def error_world(q_target, q_current):
    """Rotation vector (world frame, axis*angle, radians) taking q_current onto q_target.

    Math: the world-frame error rotation is q_err = q_target ⊗ q_current⁻¹
    (apply q_err *after* the current rotation and you land exactly on the
    target); mju_quat2Vel is its log map (quaternion → rotation vector).
    """
    q_err = mul(q_target, conj(q_current))
    out = np.empty(3)
    mujoco.mju_quat2Vel(out, q_err, 1.0)
    return out

That 3-vector is the "orientation error" input of §5's IK: spin at this angular velocity for one second and the orientation lands on target. All the arithmetic is delegated to MuJoCo's battle-tested mju_* C functions; we only wrap them so the rest of the code reads like plain math.

3.2 Forward kinematics: robot.ee_pose()

Forward kinematics (FK): given joint angles, where is the hand? MuJoCo's mj_forward(model, data) computes the world pose of every body in one call. Our "palm pose" = the last arm body's pose, offset 18 cm along the forearm (that body's ±y axis — measured from the hand mesh) to the palm center:

def ee_pose(self, arm):
    body = self.data.body(arm.ee_body_id)
    rotation = body.xmat.reshape(3, 3)          # wrist's world rotation matrix
    return Pose(body.xpos + rotation @ arm.ee_offset,  # origin + offset
                body.xquat.copy())                     # orientation = wrist's

Inverse kinematics is the other direction: given "where the hand should be", find the joint angles. FK has a unique answer computed in one line; IK generally has no closed-form answer — that's the central problem of this course, and it's §5.

§4 Targets = mocap cubes (and a mouse mode for free)

The red and green cubes from §2 are mocap bodies: no joints, no gravity, no collisions; their pose equals whatever you write into data.mocap_pos / data.mocap_quat. We decree: "where the hands should be" exists only inside these two cubes.

# The complete target read/write in robot.py (really, this is all of it):
def target_pose(self, arm):              # read: the IK asks "where to?" every frame
    return Pose(self.data.mocap_pos[arm.mocap_id].copy(),
                self.data.mocap_quat[arm.mocap_id].copy())

def set_target(self, arm, pose):         # write: a source says "go here" every frame
    self.data.mocap_pos[arm.mocap_id] = pose.pos
    self.data.mocap_quat[arm.mocap_id] = pose.quat

On reset() the cubes are parked exactly on the palms (target = current state, error = zero), so every mode starts with the robot perfectly still — nothing ever jumps is a principle that runs through the entire project.

Mouse mode: the best code is no code

MuJoCo's interactive viewer natively supports dragging mocap bodies: select one, and every viewer.sync() writes your drag straight into data.mocap_pos/quat. (We checked the MuJoCo 4.0.1 C++ source, simulate.cc: in passive mode, sync applies mjv_applyPerturbPose, which writes only to mocap bodies.) So the "mouse mode" implementation is — nothing at all:

# src/teleop/sources/__init__.py
class MouseSource(TargetSource):
    """The "do nothing" source, and that's the point: the viewer drags the
    cubes for us, and the IK only ever looks at the cubes."""
Try it uv run test-in-sim --source mouse, then: double-click the red cube to select it → Ctrl+right-drag to translate (add Shift for the horizontal plane), Ctrl+left-drag to rotate. The arm chases it in real time. Congratulations — you are already "teleoperating"; the input device just happens to be a mouse. (Rotating a cube also works in the viewer, but the K1's position-only IK ignores it — §5 explains why.)

§5 Differential inverse kinematics: the heart of the project (src/teleop/ik.py)

IK answers: "the hand is here, the target is there — how should each joint turn?" We never solve for a final configuration. Instead, 60 times a second, we answer a much smaller question:

Idea Find a joint velocity dq that nudges the hand toward the target; take one small step; look again; repeat. Target moving? Doesn't matter — we re-aim every frame, so tracking a moving VR controller comes for free. This is differential IK, and it is the industry-standard approach for VR teleoperation.

5.1 Error → desired velocity

twist = settings.pos_gain * (target.pos - current.pos)   # position error × gain

Gains have units of 1/second: "close this fraction of the error per second". pos_gain=12 means the hand rushes at 12 × error — the smaller the error, the gentler the motion. Smoothing is built in.

The DoF budget (why position only) A full pose is 6 numbers: 3 position + 3 orientation. Tracking both therefore needs at least 6 joints per arm. The K1 and the T1 both have 4 — and one of them (elbow_pitch, the pronation) spins the forearm about its own axis, so it cannot move the hand point at all: effectively 3 positional DoF + 1 spare. Orientation is simply not in the budget; asking for it anyway makes the solver trade away position accuracy chasing the impossible. Hence track_orientation=False in the spec: the error is 3-D, the jacobian keeps only its position rows, and the hand's orientation is whatever the arm geometry implies. (ik.py retains the full 6-D path — plug in a robot with ≥ 6-DoF arms, flip the flag, and orientation tracking lights up. The orientation error math lives in quat.error_world, §3.)

5.2 The jacobian: the bridge between joint and hand velocity

The jacobian J answers "if each joint turned at 1 rad/s, how would the hand move?": hand velocity = J · joint velocities. MuJoCo hands it to us:

jacp = np.zeros((3, model.nv)); jacr = np.zeros((3, model.nv))
mujoco.mj_jac(model, data, jacp, jacr, current.pos, arm.ee_body_id)  # taken at the palm point
jac = jacp[:, arm.dof_ids]   # position rows only; this arm's 4 columns → 3×4

Note the column slice uses dof_ids (the §2 pitfall): jacobians live in nv space. And you can see the pronation fact in this matrix: the elbow_pitch column is ≈ 0 — that joint moves nothing the position task cares about, which is exactly why 5.4 hands it to the posture objective.

5.3 Damped least squares (DLS): inverting without drama

We want J·dq = twist. J isn't square (3×4), and naive "division" explodes near a singularity (e.g. a fully stretched arm): some directions of hand motion become impossible, and forcing them demands infinite joint speed. The fix is a little damping λ in the inversion:

# dq = Jᵀ (J Jᵀ + λ² I)⁻¹ · twist      — textbook name: damped least squares
jjt = jac @ jac.T
jjt[np.diag_indices_from(jjt)] += settings.damping ** 2
dq = jac.T @ np.linalg.solve(jjt, twist)

Intuition for λ: accuracy traded for stability. λ=0 is the exact least-squares solution (dangerous); large λ is sluggish everywhere. We use 0.05.

5.4 The nullspace: where the spare freedom goes

Four joints chasing a 3-D point leaves one degree of freedom spare — on the K1 it is essentially the forearm pronation (5.2 showed its jacobian column is ≈ 0). Left unmanaged, spare joints slowly drift somewhere awkward. We spend the spare freedom on "gently pull toward a comfortable home posture" — but it must be projected into the nullspace (the directions where J·dq = 0), guaranteed invisible to the hand:

dq_posture = settings.posture_gain * (arm.q_home - data.qpos[arm.qpos_ids])
dq += dq_posture - np.linalg.pinv(jac) @ (jac @ dq_posture)   # (I − J⁺J)·dq_posture
Pitfall! (measured war story #1) The projection must use the exact pseudo-inverse np.linalg.pinv(jac). It is tempting to reuse the damped inverse from 5.3 — but the damping makes the projector leak posture motion into task space, which fights the tracking and parks the hand short of the target forever. Measured on the K1's static-reach test: 0.33 mm steady-state error with the damped projector vs 0.00 mm with the exact one — and the leak grows with the damping and the task dimension (on a 7-DoF arm tracking a full 6-D pose we measured it at over a centimeter). A steady-state error that no amount of waiting fixes is the signature of this bug. Reproduce it: swap the line above for jac.T @ np.linalg.solve(jjt, jac @ dq_posture) and rerun the §5 "Try it" experiment.
Pitfall! (measured war story #2) At home the K1's arms hang near the bottom of their workspace, close to singular — some motion directions are nearly impossible there and tracking turns sluggish. We measured the figure-8's worst-case error for a sweep of working-center heights: centered only 10 cm above home it is 30.5 mm; lifted 14 cm, 24.6 mm; lifted 18 cm (where §7 puts it), 9.9 mm. Same solver, three-times-better tracking — that is why the trajectory lifts the hands to the chest first: designing good targets matters as much as a good solver.

5.5 Finishing touches: speed cap, limits, integration

peak = float(np.max(np.abs(dq)))
if peak > settings.max_joint_vel:          # uniform scale-down (keeps the hand's direction)
    dq *= settings.max_joint_vel / peak
...
q = robot.data.qpos[arm.qpos_ids] + dq * dt            # integrate one small step
robot.data.qpos[arm.qpos_ids] = np.clip(q, arm.joint_min, arm.joint_max)

The speed cap protects real motors (§9 reuses it directly); limits are hard-clipped with np.clip. The two arms share no joints, so each solves its own little 3×4 problem — simpler code, simpler mental model.

Then 0.001, and drag the mouse target far out of reach — watch the jitter. ② Set posture_gain to 0 and draw figure-8s for a while — watch the elbow wander. ③ uv run pytest tests/test_ik.py -v: five convergence tests are this chapter's "proof".

§6 The simulation main loop: test-in-sim (src/teleop/run_sim.py)

Everything is in place; the main loop has exactly 4 lines of real work, 60 times per second:

targets = source.get_targets(t)   # 1. ask the source: where should the hands go? (None = no opinion)
if targets is not None:
    robot.set_targets(targets)    # 2. write into the mocap cubes
errors = ik.step(robot, dt)       # 3. each arm takes one small step toward its cube
viewer.sync()                     # 4. draw (and apply your mouse drags to the mocap cubes)
Important We never call mj_step (physics integration)! This is pure kinematics — a puppet show: the IK writes joint angles directly and mj_forward merely converts them into world poses. Benefits: the robot can never fall over, there are no motor gains to tune, and the first run never ends in frustration. Want real physics? Exercise 5 in §10 shows how to switch to position actuators + mj_step.

The rest of the file is periphery: argparse picks the source (--source trajectory|mouse|pico), a 60 Hz pacing loop (sleep off whatever time is left after the work), a tracking-error printout every 2 seconds, and the --headless mode — run N seconds without a window and exit non-zero if the final error exceeds 30 mm. That mode is the end-to-end smoke test for CI/servers, and your fastest alarm when you break the IK.

Platform note On macOS, MuJoCo's interactive viewer must run under Apple's mjpython launcher: uv run mjpython -m teleop.run_sim. run_sim detects the situation and tells you; --headless (and all tests) work under plain Python everywhere.
Try it uv run test-in-sim --headless --duration 15: watch the error fall to 5–10 mm while drawing the 8. Then deliberately set pos_gain to 1 and watch it FAIL.

No display at all (a remote server, CI)? You can still watch the robot: uv run render-videos (src/teleop/tools/render_videos.py) runs the same loop against MuJoCo's offscreen renderer and writes three MP4s into video/, named after the robot (--robot-spec; e.g. k1_01_figure8.mp4, t1_01_figure8.mp4) — the figure-8 demo, a scripted fake-headset clip that makes the clutch visible (a controller sphere flies away while the robot holds still), and a workspace-edge stress clip for §5's damping discussion. The camera framing scales off the spec's trunk height, so both robots are shot correctly with no per-robot code. Handy for slides, too.

§7 The first target source: a scripted figure-8 (src/teleop/sources/trajectory.py)

The source interface is small enough to read in one glance (src/teleop/sources/__init__.py):

class TargetSource:
    def start(self): ...                       # once, before the loop (e.g. start a server)
    def get_targets(self, t) -> TargetFrame | None: ...   # every frame: new targets, or nothing to say
    def stop(self): ...                        # once, after the loop

The trajectory source has two phases, both starting smoothly from wherever the hands are (that no-jumps principle again):

  1. Lift-in (first 3 s): smoothstep (3x²−2x³, zero velocity at both ends) carries both hands from the hanging pose to a working spot in front of the chest, LIFT_OFFSET=(0.10, 0, 0.18). The numbers come from §5's war story #2 sweep: this center tracks the 8 at 9.9 mm worst-case, versus 30.5 mm barely above the hanging pose. (The K1 tracks position only, so no orientation choreography is needed — targets keep their reset orientation forever.)
  2. The figure-8: a lemniscate in the y–z plane, right hand mirrored:
u  = 2π · (t − ramp_time) / period
Δy = A · sin(u)                 # A = 0.10 m
Δz = A/2 · sin(2u)              # double frequency → the "∞" shape
left  = rest + lift + (0, +Δy, Δz)
right = rest + lift + (0, −Δy, Δz)        # mirrored, like tai chi
Try it Set amplitude=0.12 and rerun — the edges of the bigger 8 brush the workspace boundary of the K1's 0.39 m arms (we measured worst-case error tripling to ~32 mm). Halve period: speed doubles, and lag = speed ÷ pos_gain. Predict the number, then measure it.

§8 VR: WebXR, coordinate frames, and the clutch

Time to replace the fake input with real controllers. The design choice: WebXR — a web page opened in the Pico's built-in browser reads controller poses and streams them to the PC over a WebSocket. Zero install on the headset (you open one URL), and the PC side adds a single websockets dependency. Several production humanoid-teleop stacks drive their robots from the PICO's built-in browser with this same pattern. (The research-grade alternative — PICO's XRoboToolkit, ~90 Hz native streaming + body tracking — requires building a Unity APK and adb-sideloading it onto every headset: too much setup for a classroom. See §10.)

8.1 The headset page: src/teleop/sources/webxr/index.html

One HTML file is the whole thing (no framework, no build step). The core is ~30 lines:

const session  = await navigator.xr.requestSession("immersive-vr",
                       { requiredFeatures: ["local-floor"] });  // origin on the floor beneath you
const refSpace = await session.requestReferenceSpace("local-floor");

session.requestAnimationFrame(function onFrame(time, frame) {
  session.requestAnimationFrame(onFrame);               // ~72 Hz
  for (const input of session.inputSources) {           // both controllers
    const pose = frame.getPose(input.gripSpace, refSpace);  // may be null — guard it!
    const p = pose.transform.position;      // meters; x right, y up, z backward
    const q = pose.transform.orientation;   // quaternion, xyzw order (!)
    const buttons = input.gamepad.buttons;  // xr-standard: [0]=trigger [1]=grip [4]=A/X
    ...pack into JSON...
  }
  const head = frame.getViewerPose(refSpace);  // the headset pose (for recentering, 8.3)
  ws.send(JSON.stringify({ t, left, right, head, recenter }));  // stream to the PC
});

The page does three more considerate things: it checks isSessionSupported before offering the button; it attaches a WebGL baseLayer and clears the view to a color — the world turns green while you squeeze the grip, a visceral "the robot is following me" signal; and the WebSocket auto-reconnects.

Pitfall! WebXR exists only in a HTTPS (secure) context, and requestSession must be triggered by a user click. There's no real certificate on a LAN, so we use a self-signed certificate: the browser warns once; tap "Advanced → Proceed". The page and the WebSocket share one port, so accepting the warning once unblocks both (the wss certificate exception rides along with the same origin). For wired debugging (no shared Wi-Fi needed at all): adb reverse tcp:8443 tcp:8443, then open https://localhost:8443 on the headset — the server speaks TLS only, and the generated certificate lists localhost as a valid name, so it is the same one-time warning as over Wi-Fi.

8.2 Coordinate frames: two worlds shake hands (src/teleop/mapping.py)

WebXR: x right, y up, −z forward. MuJoCo: x forward, y left, z up. Standing behind the robot, facing the same way it faces, "push the controller forward" must become "robot +x":

XR_TO_MJ_MAT = [[ 0, 0, -1],      # x_mj = -z_xr   (forward)
                [-1, 0,  0],      # y_mj = -x_xr   (left)
                [ 0, 1,  0]]      # z_mj = +y_xr   (up)
# Positions: multiply by the matrix. Orientations: conjugate by the same
# rotation, R_mj = R_fix · R_xr · R_fixᵀ
# (the same physical rotation, re-expressed in the robot's axes).

The quaternion order flip (xyzw→wxyz) happens once, where pico.py ingests each message; after that the whole repo is wxyz. tests/test_mapping.py pins the directions with known rotations ("a turn about XR's y-axis must become a turn about MJ's z-axis").

8.3 The clutch: the most important interaction design in VR teleop

Absolute mapping would require calibrating "where is the headset relative to the robot?" — nobody wants to do that in a classroom. Relative mapping with a clutch sidesteps it entirely: controller deltas apply to the target only while you hold the grip button; release and the target freezes; reposition your arm comfortably and squeeze again — the target never jumps. Exactly like lifting a mouse to re-center it on the pad.

class Clutch:                           # mapping.py, one per hand
    def update(self, grip_held, controller):
        if not grip_held: release → remember the target, drop snapshots; return frozen target
        if just gripped:  snapshot controller₀ and target₀
        # while held, every frame:
        target.pos  = target₀.pos + scale · (controller.pos − controller₀.pos)
        target.quat = unchanged — the clutch is translation-only

scale is the ergonomics knob: 0.5 = you move 10 cm, the robot moves 5 cm (precision work); 2.0 = big workspace. The --scale CLI flag feeds straight into this (pico source only). The clutch is deliberately translation-only: our robots track hand position (the §5 DoF budget), so transporting wrist rotation would only spin the target cubes confusingly while the IK ignored it. For a robot with ≥ 6-DoF arms you would transport the world-frame rotation since the grab, (controller.quat ⊗ controller₀.quat⁻¹) ⊗ target₀.quat — one line here, exercise 8 in §10.

8.3b Recentering: press A when "forward" feels wrong

The fixed frame conversion of 8.2 hides an assumption: it maps XR's −z to the robot's +x, but XR's −z is wherever you faced when the VR session started. Stand turned 90° from the robot's heading and every push comes out sideways — the single most disorienting failure in VR teleop, and calibration-free relative mapping cannot detect it by itself.

The fix is one button: face the robot's forward direction and press A (or X). The page streams the headset pose along with the controllers; on the button's rising edge, the server computes the yaw of your gaze and stores the opposite rotation (mapping.recenter_correction), which is applied to every raw controller sample before the XR→MJ conversion. Three design points worth noticing:

  • Yaw only. The correction rotates about XR's up axis — your gaze projected to the horizontal plane. A tilted or nodding head must not tilt the robot's world (looking straight up/down makes yaw undefined, so the server ignores the press and tells you to look level).
  • No position correction needed. The clutch works on deltas, and rotating a delta's endpoints rotates the delta — where you stand never mattered, only which way you face.
  • No jumps. Recentering disengages both clutches, exactly like releasing the grip: re-grab and continue in the fixed frame. The view flashes blue so you know it took effect.

8.4 The PC-side server: src/teleop/sources/pico.py

One port does two jobs: a plain HTTPS GET returns the page above, and /ws upgrades to a WebSocket (the websockets library's process_request hook). The server runs an asyncio loop in a background thread; when the 60 Hz main loop comes asking, it reads only the latest message (an old pose is worthless, hence no queue):

def get_targets(self, t):
    with self._lock:
        snap = self._latest
    if snap is None or time.monotonic() - snap.received_at > STALE_AFTER:
        ... disengage both clutches ...
        return None            # watchdog: data stream died → targets freeze, robot holds
    # per hand: recenter yaw fix (8.3b) → XR→MJ conversion → clutch → new target
    return TargetFrame(left=..., right=...)

On first run it generates a self-signed certificate into .certs/ with cryptography (SAN includes your LAN IP) and prints the URL the headset should open. If the laptop later moves to a different network, the cached certificate no longer covers the new IP — the server notices and regenerates it automatically.

Four robustness details worth reading in the code (each one started life as a reviewer-found bug): start() returns only once the server is actually listening, and raises a clear error if the port is taken (no false "ready" banner); only one headset may drive at a time — a second simultaneous client is politely closed (imagine two students' controllers fighting over one clutch: the target would teleport between their hands); a malformed message is logged and skipped instead of killing the connection; and stop() is safe to call at any moment, even if the server never managed to start.

Try it Put the PC and the Pico on the same Wi-Fi, run uv run test-in-sim --source pico, and follow the three printed steps. No headset handy? Run uv run pytest tests/test_pico_bridge.py -v and read how a "fake headset" walks the entire WSS pipeline (it proves: pushing 10 cm forward in XR = robot +x 10 cm; release freezes; a dead stream freezes).

§9 Connecting a real robot: test-in-real and safety (src/teleop/run_real.py)

Here's the trick: "real mode" still runs MuJoCo. The simulated robot becomes the kinematic brain — sources move the cubes and the IK chases them exactly as before — and each tick (50 Hz) adds one line: read the simulated arm joint angles and send them to the real robot's position controller.

targets = source.get_targets(t)
if targets is not None:          # None ⇒ watchdog/deadman: hold position
    brain.set_targets(targets)
ik.step(brain, dt)               # sim joints chase the targets (limits + speed cap)
real.send_joint_targets(brain.joint_targets())   # ...and the real robot copies the sim

Safety is layered. Learn the order (AGENTS.md forbids removing any layer):

LayerMechanismWhere
0 Gatesa non-dryrun robot requires the pico source (it alone has a deadman+watchdog); command rates in the IK's unstable zone are rejected run_real.py argparse
1 Deadmantargets move only while the grip is heldthe clutch (§8.3)
2 WatchdogVR stream silent 0.5 s → targets freezepico.py get_targets
3 Motion limitshard joint-limit clip + per-joint speed capik.py (§5.5)
4 On-robot checksthe hardware driver must re-verify limits itselfreal_robot.py contract
Pitfall! (why layer 0 exists) The IK integrates with explicit Euler: per tick the error is multiplied by (1 − gain·dt). That is stable only while gain·dt < 2. With pos_gain = 12/s, commanding at 5 Hz (dt = 0.2 s) gives gain·dt = 2.4 — we measured the streamed commands flipping ±27° every tick at the full velocity cap: a violent limit cycle, not tracking. Try uv run test-in-real --rate 5: it refuses, and now you know exactly why. (Also: --source mouse only exists in test-in-sim — it is the viewer that moves the targets.)

The hardware interface: src/teleop/real_robot.py

All of hardware is compressed into three methods, addressed by MuJoCo joint name:

class RealRobot:
    def connect(self): ...                         # connect; enter compliant/low-gain mode
    def send_joint_targets(self, targets: dict[str, float]): ...  # joint angles [rad] at 50 Hz
    def disconnect(self): ...                      # stop motion; must be safe to call twice

The default implementation, DryRunRobot, prints instead of moving, so uv run test-in-real is always safe to run. The real driver lives in its own module and is selected with --robot k1 or --robot t1 (the IK brain's --robot-spec then follows automatically — a K1 brain emits K1 joint names, which a T1 would not recognize, so a mismatch is refused at the argparse gate).

The real driver: src/teleop/booster.py

Booster's SDK is the optional hardware extra (uv sync --extra real; Linux-only binary wheels, which is why it is not a core dependency). One driver serves both robots, because the SDK speaks one protocol for the whole family — the robots differ only in a joint name table and a motor count. The driver is built around one key robot feature, UpperBodyCustomControl: the robot keeps balancing itself, we only borrow the arms. The onboard controller never stops owning the legs, so balance never becomes our problem — and "letting go" just hands the arms back to a robot that is still standing. (The alternative, RobotMode.kCustom, is full low-level control of every motor: you would inherit the balance problem along with them.)

connect() runs in three phases:

  1. Reach the robot: ChannelFactory.Instance().Init(0, iface) — the SDK talks Fast DDS over the LAN (--iface picks the network interface) — then B1LocoClient for mode-change RPCs.
  2. Stand up (only with --stand): ChangeMode(RobotMode.kPrepare) brings the robot into its two-foot standing posture, then ChangeMode(RobotMode.kWalking) activates the balance controller. If the robot is already standing (e.g. brought up with Booster's remote), omit the flag.
  3. Take over the arms: read one state message from rt/low_state to learn the measured arm pose, call UpperBodyCustomControl(True), and start publishing LowCmd messages at 50 Hz.

Each LowCmd carries all of the robot's motors (22 on the K1, 23 on the T1), but only the 8 arm entries carry gains (kp=60, kd=1.5, Booster's own example values). Every other motor is sent kp = kd = 0 — a zero-gain command is "no command", which is exactly what leaves those motors to the onboard balance controller (on the T1 that includes the waist). Two more details worth copying into any driver you ever write:

  • Soft start: for the first 2 s, commands blend from the measured arm pose to the IK's pose (arm_setpoints, a pure function — see its tests), so takeover can never make the arms jump.
  • Re-clamp (safety layer 4): targets are clipped to the joint limits again inside the driver, even though the IK already did it. A driver never trusts its caller.

JOINT_TO_MOTOR holds one table per robot, mapping our MuJoCo joint names to the SDK's motor indices: JointIndexK1 for the K1 (head = 0–1, arms = 2–9, legs = 10–21) and JointIndex for the T1 (head = 0–1, arms = 2–9, waist = 10, legs = 11–22). Happily the arms sit at motors 2–9 on both — only the names differ (the K1's aa-prefixed shoulders again). The names come verbatim from the model files, so each table's keys line up with robot.joint_targets() automatically — and a unit test pins each table against its RobotSpec. That is the whole §2.5 recipe finished: a new robot is one RobotSpec, one scene file, and one eight-entry table here — the IK, the sources, and the main loops don't change by a single line.

Before the first real run Keep a hand on the e-stop. Verify your robot's firmware accepts UpperBodyCustomControl (SDK ≥ 1.6; Booster's gated docs list the firmware minimum). On disconnect() the driver calls UpperBodyCustomControl(False) — arms back to the robot, which keeps standing; it deliberately does not drop into damping mode, because a damped robot falls.
Try it ① Rehearse the whole real-robot pipeline without a headset: uv run test-in-real --source trajectory --duration 5 — watch the 50 Hz joint command stream print. ② With the headset: uv run test-in-real (defaults: pico source + dry-run robot). ③ With a robot on the LAN: uv sync --extra real, then uv run test-in-real --robot k1 --stand — the K1 stands up, balances, and your controllers drive its hands (--robot t1 for a T1: same flow, the T1 joint table and the T1 IK brain are picked automatically). ④ Thought experiment: why does the watchdog freeze the targets rather than emergency-stopping the motors? §10 Exercises and further reading

Exercises (easy → hard)

  1. Change the trajectory: turn the figure-8 into a circle, then into your initials. You may only touch src/teleop/sources/trajectory.py.
  2. Reproduce both pitfalls: follow the two "Pitfall!" boxes in §5 and reproduce each once, with an error-curve screenshot. You only truly understand a fix once you can resurrect the bug.
  3. Trigger → gripper: the WebXR messages already carry trigger (0–1). Wire it to a printout/visualization (the base K1 has no hands; grippers and dexterous hands are optional add-ons that the real robot drives via the SDK's ControlGripper / ControlDexterousHand calls).
  4. The head as a camera gimbal: the K1 has 2 head joints (aahead_yaw_joint, aahead_pitch_joint) that the teleop ignores. Make the head look at the midpoint of the two hand targets every frame (hint: it's two atan2 calls on the midpoint in the head's frame — no jacobian needed for 2 joints).
  5. Real physics: K1_22dof.xml ships raw torque motors, not position servos. Weld the trunk to the world (one <equality><weld> element in the scene — otherwise the robot falls, nothing balances it), then drive the arms with your own PD law tau = kp·(q* − q) − kd·q̇ into data.ctrl and mj_step. Compare with puppet mode: does it lag? oscillate? Which kp/kd feel like the real driver's values (kp=60, kd=1.5)?
  6. The research-grade pipeline: replace the WebXR source with PICO's XRoboToolkit (PC service + Unity client + pip install xrobotoolkit-sdk) — one new TargetSource is all it takes; that's what the interface is for.
  7. Drive the real robot: bring up booster.py on hardware (§9 walks through the driver). First run: verify JOINT_TO_MOTOR against the SDK's enums (JointIndexK1 for the K1, JointIndex for the T1), halve ARM_KP, keep a hand on the e-stop, and only then try uv run test-in-real --robot k1 --stand (or --robot t1). Then extend the driver: ramp the gains back up, and add the head motors (0–1) once you have done exercise 4.
  8. Rotation through the clutch: the clutch is translation-only (§8.3). Re-add rotation transport — target.quat = (controller.quat ⊗ controller₀.quat⁻¹) ⊗ target₀.quat in Clutch.update — and verify with the viewer that the target cubes now follow your wrist. Then explain why the robot's hands still don't rotate (hint: §5's DoF budget), and what robot you'd need for them to.
